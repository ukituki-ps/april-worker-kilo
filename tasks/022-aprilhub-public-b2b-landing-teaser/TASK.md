- **Приоритет:** обычный (продуктовый маркетинг + публичный контур)
- **Зависимости:** логически продолжает [`tasks/016-aprilhub-guest-landing-entrypoint/TASK.md`](../016-aprilhub-guest-landing-entrypoint/TASK.md) (guest-зона и ingress уже есть).

## Цель
Заменить/расширить текущий неавторизованный лендинг в `hub-shell` до **полноценного публичного B2B-тизера** для внешних покупателей: **карта возможностей экосистемы April**, этапы поставки, процесс внедрения, статус развития, безопасность, FAQ и форма заявки — при этом лендинг остаётся **единой точкой входа в продукт**: с него пользователь по-прежнему переходит в **авторизованную зону** через **тот же Keycloak OIDC flow** (`keycloak.login()`), что и сейчас, без обхода единого ingress. Дизайн — дизайн-системное оформление (Mantine + токены April).

- Тесты: [`hub-shell/src/App.test.tsx`](../../hub-shell/src/App.test.tsx), [`hub-shell/tests/e2e/smoke.spec.ts`](../../hub-shell/tests/e2e/smoke.spec.ts) — обновить под новую структуру DOM/якоря, сохранить проверку guest → login CTA.
- Сборка/проверки: `npm --prefix hub-shell run build`, `npm --prefix hub-shell run test`; при изменении e2e — `npm --prefix hub-shell run e2e` (по [`docs/TESTING_STRATEGY.md`](../../docs/TESTING_STRATEGY.md)).

## Входит в объём

### Вход в авторизованную зону (обязательно)
- Лендинг — не «витрина без продукта»: **вход в авторизованную зону** реализуется тем же механизмом, что в [`016`](../016-aprilhub-guest-landing-entrypoint/TASK.md): вызов **`keycloak.login()`** после клика по кнопке (или эквиваленту), далее зоны `transition` → загрузка `/v1/me` → `authorized` с `AppShell` / `CompositionLayer` — **поведение не регрессировать**.
- **Primary CTA** по смыслу — **«Войти» / «Открыть рабочее пространство»** (или согласованная формулировка), всегда запускающая login flow. Вторичный CTA — заявка/форма (якорь `#contact` или отдельная кнопка).
- **Повторение точки входа:** минимум **два** явных места на длинной странице — **Hero** и **финальный блок** перед footer (и опционально пункт в sticky-меню: «Вход»). Все кнопки входа вызывают **одну и ту же** функцию старта login (без дублирования логики разъехавшимся кодом).
- После успешного входа пользователь попадает в **текущую** авторизованную оболочку без ручной правки URL/портов (как smoke в `016`).

### Контент и структура страницы (порядок секций)
1. **Hero** — H1, подзаголовок, **primary CTA = вход в авторизованную зону (Keycloak)**, secondary = якорь на форму заявки / «Запросить контакт», строка доверия.
2. **Для кого (ICP)** — три колонки: бизнес/операции, IT, ИБ/комплаенс.
3. **Проблема рынка** — кратко 4 боли + переходный абзац.
4. **Карта возможностей платформы** (центральный блок):
   - пять контуров: пользовательский смысл **первая строка**, продуктовое имя **вторая строка**:
     - Единая точка входа — **AprilHub**
     - Процессы — **AprilWorkFlow**
     - Коммуникации — **AprilNFlow**
     - Мастер-данные (оргструктура + профили) — **AprilOrgFlow · AprilProfile** + одна фраза, зачем два контура.
     - Отчёты — **AprilReport**
   - отдельный подраздел **«Данные и внешний контур»** — **AprilEDC** (не смешивать с пятью «опытными» контурами).
5. **Этапы развития** — таблица фаз: Architecture & design → Platform foundation → Vertical slice → Pilot → Scale-out + абзац связи с картой возможностей.
6. **Текущий статус** — легенда (Доступно / Пилот / В разработке / По дорожной карте) + таблица по продуктам; допустимы **плейсхолдеры**, вынесенные в конфиг.
7. **Как проходит проект с заказчиком** — этапы + роли со стороны заказчика.
8. **Безопасность и данные** — короткий список; ссылки на политики — только если документы есть в репо, иначе заглушки «появятся позже» или раздел без мёртвых ссылок (выбрать один вариант и зафиксировать в `REPORT.md`).
9. **Прозрачность развития** — тестирование, релизы, changelog (плейсхолдеры допустимы).
10. **FAQ** — минимум 6 вопросов (в т.ч. интеграции, пилот, развёртывание, разделение OrgFlow/Profile, EDC).
11. **Финальный CTA + форма заявки** (см. ниже).
12. **Footer** — контакты/юр. плейсхолдеры, «последнее обновление страницы».

### Навигация
- Sticky или верхнее **якорное меню** по секциям: Зачем · Карта · Этапы · Статус · Внедрение · Безопасность · FAQ · Контакты (идентификаторы `id` согласованы с меню).
- В меню или рядом — отдельный элемент **«Вход»** (или кнопка), ведущий на **тот же** login flow, что и primary CTA (не якорь по странице).

### Реализация в коде
- Вынести контент в **отдельный модуль** (например `hub-shell/src/landing/` или `hub-shell/src/guest-marketing/`), типизированный объект/константы, чтобы править тексты без правок разметки.
- Компоненты секций на **Mantine** (`Stack`, `Card`, `Table`, `Anchor`, `SimpleGrid`, и т.д.), визуальная согласованность с текущим guest-лендингом и дизайн-системой.
- **Доступность:** осмысленная иерархия `h1`–`h3`, фокус для клавиатуры, контраст по возможности.
- **Форма заявки** (минимум полей): компания, страна, роль, масштаб (select или текст), комментарий, опционально согласие на обработку ПДн.
  - Проверить, есть ли в `hub-bff` готовый endpoint для лидов; если **нет** — реализовать **безопасный MVP**: клиентская валидация + `mailto:` с телом письма **или** явный TODO + неотправляемая форма с сообщением «backend в backlog» (предпочтительнее рабочий `mailto:` или ссылка на корпоративную почту). Поведение описать в `REPORT.md`.

### Тестирование
- Обновить unit-тесты: guest-зона рендерится, ключевые секции/якоря или `data-testid` присутствуют, CTA входа в Keycloak не сломан.
- Обновить/расширить e2e smoke при необходимости (видимость guest, клик по login).

## Не входит в объём
- Отдельный микросервис или БД для лидов (если не согласовано — только заглушка/TODO).
- Многоязычность (i18n).
- Полноценная CMS.
- Изменение модели IAM/RBAC, контрактов `hub-bff` OpenAPI — только если явно требуется для отправки формы и согласовано отдельно.
- Редизайн авторизованной зоны (`AppShell` после входа) сверх минимальных правок, если они неизбежны.

## Технические ограничения
- Стек: React + TypeScript + Vite + Mantine + Keycloak; не ломать существующий **login flow** и единый ingress.
- Имена продуктов **без опечаток:** AprilHub, AprilWorkFlow, AprilNFlow, AprilOrgFlow, AprilProfile, AprilReport, AprilEDC.
- Не утверждать как факт сертификации, SLA, наличие клиентов без подтверждения в репозитории/доках.
- Секреты и credentials не коммитить.
- Пользовательские тексты — **русский**.
