# Задача: Hub Data & Runtime Dependencies Readiness (Этап 007)

## Мета
- **ID / ветка:** `007-hub-data-runtime-readiness`
- **Приоритет:** высокий
- **Связанные документы:** `task_list.md`, `tasks/000-aprilhub-full-service-roadmap/TASK.md`, `tasks/006-hub-observability-operability/REPORT.md`, `docs/architecture/APRILHUB_C3_C4.md`, `docs/architecture/C4_RUNTIME_SEQUENCES.md`, `docs/architecture/INTEGRATION_CONTRACTS.md`, `docs/TESTING_STRATEGY.md`, `docs/DEPLOYMENT_STRATEGY.md`

## Цель
Подготовить `AprilHub` к следующему этапу стабилизации (`008`) с точки зрения data/runtime зависимостей: зафиксировать, нужен ли `hub-bff` persistence-контур, и при подтверждённой необходимости реализовать минимально необходимую схему хранения и/или фоновую обработку (очередь/воркер) без выхода за границы BFF-агрегации.

## Контекст для агента
- После этапа `006` в `hub-bff` реализованы observability baseline и smoke-проверки.
- `AprilHub` по архитектуре остаётся UI/BFF слоем и не становится доменным оркестратором.
- Этап `007` является readiness-этапом перед полным закрытием тестовых и деплойных эпиков `008/009`.
- Любые data-изменения допустимы только как техническая поддержка runtime `hub-bff` (например, idempotency/runtime-state), а не новая бизнес-доменная модель.
- При добавлении persistence требуется полная воспроизводимость локально/в CI и согласование с существующими контейнерными профилями.

## Входит в объём
- Провести ревизию текущих runtime потребностей `hub-bff`:
  - какие сценарии уже закрываются stateless-подходом,
  - какие сценарии требуют минимального хранения состояния или фоновой обработки.
- Зафиксировать решение по persistence:
  - если не требуется — явно документировать это как результат этапа,
  - если требуется — реализовать минимальную схему (только технические сущности) через Atlas.
- При необходимости добавить базовый queue/worker контур для технических задач:
  - только для вспомогательных runtime-функций `hub-bff`,
  - с идемпотентностью и контролируемой retry-политикой.
- Доработать конфигурацию и локальный runtime:
  - env-параметры для зависимостей (PostgreSQL/Redis/worker), если они добавлены,
  - compose/runtime wiring для воспроизводимых локальных и CI запусков.
- Добавить/обновить тесты и проверки:
  - unit/integration на idempotency/state transitions/ошибки зависимостей (если появляется persistence/queue),
  - smoke на отсутствие регрессий auth/aggregation/degraded path.
- Синхронизировать task-артефакты этапа:
  - `PLAN.md` (детализация шагов реализации),
  - `REPORT.md` (что внедрено, что сознательно не внедрено и почему).

## Не входит в объём
- Проектирование новой бизнес-доменной БД для AprilHub.
- Миграция или изменение схем downstream-сервисов экосистемы April.
- Перепроектирование API-контрактов этапа `005` вне необходимости совместимости.
- Замена Keycloak-first auth-модели или обход RBAC.
- Отдельный инфраструктурный проект по очередям/хранилищам вне нужд `hub-bff`.

## Технические ограничения
- Архитектурные границы AprilHub не меняются: только UI-агрегация и адаптация DTO.
- Любые изменения схемы БД выполнять только через Atlas.
- Новые runtime зависимости вводить только при подтверждённой необходимости и минимальном blast radius.
- Не коммитить секреты/токены; значения конфиденциальных переменных не хранить в репозитории.
- Совместимость с текущими OpenAPI контрактами и auth/RBAC runtime обязательна.

## Принятое решение этапа 007
- `hub-bff` остаётся полностью stateless на текущем scope aggregation/readiness.
- Persistence-контур (PostgreSQL + Atlas migrations) **не требуется**: в runtime нет durable state/idempotency key store, а retry/degraded логика укладывается в один request lifecycle.
- Queue/worker контур (Redis/Asynq) **не требуется**: отсутствуют async side effects и фоновые задачи, выходящие за границы BFF-агрегации.
- Follow-up переносится на этапы `008/009`: перепроверка решения при появлении новых сценариев с техническим состоянием или deferred processing.
