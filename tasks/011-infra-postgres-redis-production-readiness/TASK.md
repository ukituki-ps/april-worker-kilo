# Задача: Infra PostgreSQL/Redis Production Readiness (Этап 011)

## Мета
- **ID / ветка:** `011-infra-postgres-redis-production-readiness`
- **Приоритет:** высокий
- **Связанные документы:** `task_list.md`, `tasks/000-aprilhub-full-service-roadmap/TASK.md`, `docs/DEPLOYMENT_STRATEGY.md`, `docs/TESTING_STRATEGY.md`, `docs/AGENT_ARCHITECTURE_CONTEXT.md`, `docs/architecture/INTERSERVICE_LINKS.md`

## Цель
Подготовить production-grade инфраструктурный контур PostgreSQL и Redis для сервисов April (включая AprilHub runtime зависимости): определить и внедрить устойчивую схему развертывания, резервного копирования, мониторинга, безопасности и процедур эксплуатации/восстановления, отделённую от application-level задач этапов `001-010`.

## Контекст для агента
- Этапы `007-010` закрывают application/runtime readiness AprilHub; `011` является отдельным platform/infra треком.
- В рамках April стека PostgreSQL и Redis используются как базовые инфраструктурные зависимости и должны поддерживать эксплуатационные требования dev->prod.
- На этапе `011` фокус не на бизнес-логике приложений, а на надёжности платформенного data-layer.
- Любые изменения приложения в `011` допускаются только как адаптация к новой инфраструктурной конфигурации (env/connection/policies), без расширения продуктового scope.

## Входит в объём
- Спроектировать и зафиксировать target-state для PostgreSQL/Redis:
  - topology/HA-уровень (по бюджету и требованиям),
  - границы ответственности platform vs application teams.
- Внедрить production-ready контур для PostgreSQL:
  - стратегия бэкапов (полные + инкрементальные/журналы по принятому процессу),
  - проверяемый restore-процесс и регулярная валидация восстановления,
  - базовые политики доступа и hardening.
- Внедрить production-ready контур для Redis:
  - режим эксплуатации (persistence/replication/sentinel или эквивалент по согласованию),
  - политика отказоустойчивости и восстановления,
  - политика безопасности и ограничение доступа.
- Наблюдаемость и операционность:
  - метрики/алерты на доступность, latency, saturation, storage/memory pressure,
  - runbooks на инциденты PostgreSQL/Redis (degraded, failover, restore).
- Интеграция с текущим deployment-процессом:
  - описать и зафиксировать порядок изменений в `docs/DEPLOYMENT_STRATEGY.md` (или связанном platform документе),
  - подтвердить совместимость с существующим flow образов/rollout/rollback.

## Не входит в объём
- Реализация новых бизнес-фич в сервисах April.
- Масштабный рефакторинг application-кода вне необходимой конфигурационной адаптации.
- Замена базового технологического стека (PostgreSQL/Redis) на альтернативы.
- Миграция всех сервисов экосистемы на новые контуры в один релиз без staged rollout.

## Технические ограничения
- Следовать принятому стеку April: PostgreSQL + Redis остаются целевыми технологиями.
- Не коммитить секреты, ключи, пароли и приватные сертификаты.
- Изменения схем сервисных БД — только через Atlas в соответствующих репозиториях/сервисах.
- Избегать необратимых изменений без проверенного rollback/restore сценария.
- Документация по эксплуатации обязательна к синхронизации с фактической реализацией.
