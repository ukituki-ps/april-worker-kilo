# Задача 026: анализ подходов AprilProfile к фронтенду/DS и синхронизация документации AprilHub

## Мета
- **ID / ветка:** `026-aprilhub-align-docs-with-april-profile-design-system-approach`
- **Приоритет:** высокий
- **Тип:** [документация, межрепозиторная синхронизация]
- **Связанные документы:**
  - `../april-profile-1/docs/FRONTEND_STRATEGY.md`
  - `../april-profile-1/docs/guides/DESIGN_SYSTEM.md`
  - `../april-profile-1/docs/WIDGET_CONTRACTS.md`
  - `docs/README.md`
  - `docs/AGENT_MASTER_PROMPT.md`
  - `task_list.md`

## Цель
Просмотреть и проанализировать, как в `april-profile-1` организованы фронтенд-подходы и работа с дизайн-системой (`@april/tokens`, `@april/ui`, DisignApril), после чего привести документацию `april-worker` к согласованному виду без расхождения терминов, контрактов и практик интеграции.

## Контекст для агента
- В `april-profile-1` зафиксирована целевая модель интеграции UI (Host-driven / Widget-driven / API/BFF-first) и границы ответственности между DS, domain widgets и host.
- Также формализованы правила подключения DS как submodule, сборка `ds:prepare`, ожидания по `AprilProviders`, недопустимые anti-patterns и связь с контрактами виджетов.
- Документация `april-worker` должна описывать эти же принципы в том объёме, который относится к AprilHub, без конфликтов формулировок.

## Входит в объём
- Проанализировать документы `april-profile-1`, связанные с frontend strategy и DS-гайдлайнами.
- Выявить расхождения между `april-profile-1` и текущей документацией `april-worker` по:
  - терминологии (host/widget/contract),
  - правилам использования DS,
  - границам ответственности между shell, widgets и UI primitives.
- Обновить релевантные документы `april-worker` так, чтобы:
  - описания подходов были консистентны с `april-profile-1`,
  - были сохранены локальные особенности AprilHub,
  - не появилось дублирования и взаимоисключающих инструкций.
- Зафиксировать, какие документы обновлены и какие принципы синхронизированы.

## Не входит в объём
- Реализация новых UI-фич или рефакторинг фронтенд-кода вне задач документации.
- Изменение API-контрактов, backend-логики и деплой-пайплайнов.
- Перенос всех документов AprilProfile в AprilHub «как есть» без адаптации контекста.

## Технические ограничения
- Не менять принятый стек (`React + TypeScript + Vite`, Mantine, DisignApril), если это не требуется постановкой.
- Не вводить новые источники истины: синхронизация должна опираться на уже существующие документы `docs/`.
- Все спорные или неоднозначные расхождения фиксировать явно в отчёте/заметках задачи.
