# Стратегия фронтенда AprilHub и интеграция доменных виджетов

> Документ синхронизирован с подходом `april-profile-1` и адаптирован под контекст `april-worker` (AprilHub как host).

**Статус:** согласованная модель для AprilHub  
**Связанные документы:** [`guides/DESIGN_SYSTEM.md`](./guides/DESIGN_SYSTEM.md), [`WIDGET_CONTRACTS.md`](./WIDGET_CONTRACTS.md), [`AGENT_ARCHITECTURE_CONTEXT.md`](./AGENT_ARCHITECTURE_CONTEXT.md), [`TESTING_STRATEGY.md`](./TESTING_STRATEGY.md), [`architecture/INTEGRATION_CONTRACTS.md`](./architecture/INTEGRATION_CONTRACTS.md)

---

## 1. Цели

- **Единый визуальный язык**: `@april/tokens`, `@april/ui`, Mantine.
- **Предсказуемая интеграция UI-модулей**: host-страницы и встраиваемые виджеты работают по единым контрактам.
- **Безопасная мультитенантность**: `tenant` и auth-контекст берутся только из доверенного слоя (OIDC/BFF), не из пользовательского ввода.
- **Минимум дублирования**: повторно используемый UI и API-клиенты выносятся в domain-пакеты, а не копируются между экранами.

---

## 2. Модели интеграции UI

Термины используются в том же значении, что и в `april-profile-1`.

### 2.1 Host-driven

Экран полностью реализован в AprilHub.

- **Когда использовать:** сложная IA, уникальные операционные сценарии, слабое переиспользование.
- **Риски:** рост дублирования при отсутствии выделения общих виджетов/примитивов.

### 2.2 Widget-driven

Host встраивает React-виджеты из `@april/*-ui`.

- **Когда использовать:** один и тот же UX нужен в нескольких сервисах/контекстах.
- **Риски:** требуется semver-дисциплина и явная совместимость host × widget.

### 2.3 API/BFF-first

Host работает через API/BFF без развитого слоя виджетов.

- **Когда использовать:** ранняя фаза фичи, когда нужен быстрый запуск без полного UI-пакета.
- **Риски:** долгосрочный разъезд UX и повторная реализация одинаковых экранов.

## 3. Границы ответственности

| Слой | Ответственность |
|------|-----------------|
| **Design System** (`@april/tokens`, `@april/ui`) | Визуальные примитивы, тема, a11y; без доменной логики и tenant/API-правил. |
| **Domain widgets** (`@april/*-ui`) | Доменный UI, локальный state формы, вызовы API в границах сценария, эмиссия типизированных событий. |
| **Host pages (AprilHub)** | Router, layout, OIDC/RBAC контекст, сценарный state, обработка событий виджета и навигационных intent. |

---

## 4. Обязательные интеграционные правила для AprilHub

1. **Один root Router и один набор корневых провайдеров** (`AprilProviders`, Mantine theme) в host.
2. **Виджет не владеет глобальной навигацией**: прямой `navigate`/`window.location` заменяется событиями в host.
3. **HostContext обязателен**: минимум `tenant`, `auth`, `theme`, `locale`, `telemetry.requestId`.
4. **RBAC/ABAC не дублируется во frontend**: права определяются Keycloak и backend-политиками.
5. **Наблюдаемость сквозная**: `requestId` должен проходить цепочку host -> BFF -> downstream API.

Подробный формат контракта: [`WIDGET_CONTRACTS.md`](./WIDGET_CONTRACTS.md).

---

## 5. Практика интеграции в этом репозитории

- DS подключается через `design-system/DisignApril` и локальные `file:` зависимости в `hub-shell` (см. [`guides/DESIGN_SYSTEM.md`](./guides/DESIGN_SYSTEM.md)).
- Подготовка DS перед dev/build/test выполняется через `ds:prepare`.
- Для новых виджетов сначала фиксируется контракт host/widget, затем сценарий встраивания в shell.

---

## 6. Мини-чеклист перед мерджем UI-интеграции

1. Термины и зона ответственности соответствуют этому документу.
2. Встраиваемый виджет не монтирует собственные глобальные провайдеры.
3. События виджета типизированы и обрабатываются host-ом.
4. Tenant/auth берутся из доверенного контекста, а не из формы/query.
5. Документация по интеграции обновлена вместе с изменением кода.
