# AprilWorker: C3 и C4

Документ описывает `AprilWorker` на детальных уровнях C4-модели:
- **C3 (Component)** — компоненты внутри контейнеров `AprilWorker API` и `AprilWorker Engine`.
- **C4 (Code)** — runtime-потоки, модули оркестрации и механики исполнения бизнес-логики.

Базовые источники:
- `structurizr/workspace.dsl`
- `docs/architecture/INTERSERVICE_LINKS.md`
- `docs/architecture/INTEGRATION_CONTRACTS.md`

## 1. Роль AprilWorker в системе

`AprilWorker` — централизованный сервис исполнения сквозной бизнес-логики между доменными микросервисами.

Основная задача:
- вынести кросс-доменные правила из UI/BFF и отдельных доменов;
- оркестрировать последовательности вызовов и компенсаций;
- запускать бизнес-сценарии с контролем состояния и наблюдаемостью.

`AprilWorker` не является owner доменных данных, а использует контракты доменных сервисов.

## 2. C3: Компоненты AprilWorker

### 2.1 Компоненты `AprilWorker API`

1. **Scenario Entry API**
   - Принимает команды запуска бизнес-сценариев.
   - Нормализует входные параметры и передаёт их в orchestrator.

2. **Auth/Policy Guard**
   - Проверяет сервисные права и контекст вызова.
   - Блокирует запуск запрещённых сценариев.

3. **Scenario Resolver**
   - Сопоставляет запрос с типом сценария/процесса.
   - Определяет нужный шаблон шагов и правила ветвления.

4. **Orchestration Coordinator**
   - Строит execution plan для синхронных и асинхронных шагов.
   - Вызывает downstream-контракты (Workflow/NFlow/OrgFlow/Profil/EDC/Report).

5. **Contract Adapter Layer**
   - Единый слой клиентов к внешним API сервисов.
   - Управляет timeout/retry/circuit-breaker по контрактам.

6. **Result Aggregator**
   - Формирует итог исполнения сценария (успех, частичный успех, ошибка, компенсация).

### 2.2 Компоненты `AprilWorker Engine`

1. **Job Dispatcher**
   - Ставит фоновые шаги в очередь (`Redis + Asynq`).
   - Управляет приоритетами и маршрутами исполнения задач.

2. **Scenario Executor Workers**
   - Исполняют фоновые шаги и длительные операции.
   - Поддерживают state machine сценария.

3. **Compensation Handler**
   - Выполняет компенсационные действия при сбоях на поздних шагах.
   - Гарантирует консистентное завершение сценария.

4. **State Store Adapter**
   - Сохраняет статус сценариев и шагов в `PostgreSQL`.
   - Хранит журнал решений, ошибок и повторов.

5. **Retry & Dead-letter Controller**
   - Управляет политикой повторов.
   - Переводит безуспешные задачи в fail-state/DLQ-подобный контур (по проектным правилам).

6. **Observability Emitter**
   - Публикует метрики, техсобытия и корреляционные идентификаторы.

## 3. C4: Code-level поведение AprilWorker

### 3.1 Flow запуска сценария

1. Вызов приходит в `Scenario Entry API`.
2. `Auth/Policy Guard` проверяет права вызова.
3. `Scenario Resolver` выбирает шаблон сценария.
4. `Orchestration Coordinator` строит план шагов.
5. Синхронные шаги выполняются сразу через `Contract Adapter Layer`.
6. Длительные шаги передаются в `AprilWorker Engine` через очередь.
7. Итог собирается `Result Aggregator` и возвращается вызывающему сервису.

### 3.2 Flow гибридной оркестрации (sync + async)

- **Sync часть**:
  - быстрые проверки контекста (`OrgFlow`, `Profil`, `WorkFlow`) с жёстким timeout;
  - инициация внешних действий (`NFlow`, `EDC`, `Report`) через контракты.
- **Async часть**:
  - долгие этапы ставятся в очередь;
  - worker обрабатывает задачу, обновляет статус и при необходимости инициирует следующий шаг.

### 3.3 Flow обработки ошибок и компенсаций

1. Ошибка шага фиксируется в журнале состояния.
2. Если шаг ретраебелен — выполняется retry по политике.
3. Если ошибка фатальная — запускается `Compensation Handler`.
4. Сценарий завершаетcя в одном из состояний:
   - `Completed`
   - `CompletedWithCompensation`
   - `Failed`

### 3.4 Flow идемпотентности

- У каждого сценария есть `scenarioId` и `correlationId`.
- Повторный запрос с тем же id не создаёт дубликат выполнения.
- Worker-обработчики обязаны быть идемпотентными.

### 3.5 Flow интеграции с EDC

`AprilWorker` может запускать интеграционные задачи через `AprilEDC`.

Типовой порядок:
1. `AprilWorker API` -> `AprilEDC API`: запуск задачи интеграции.
2. `AprilEDC` выполняет загрузку/нормализацию.
3. Результаты возвращаются в доменные сервисы асинхронно по согласованным контрактам.
4. `AprilWorker` учитывает статус задачи в бизнес-сценарии.

## 4. Границы ответственности

`AprilWorker` отвечает за:
- кросс-доменные бизнес-правила;
- порядок вызовов и управление состоянием сценариев;
- компенсации и устойчивость исполнения.

`AprilWorker` не отвечает за:
- хранение master-данных доменов;
- внутренние правила доменного микросервиса;
- UI-оркестрацию (это зона `AprilHub`).

## 5. Минимальные технические требования

- Обязательная передача `correlationId` во все downstream вызовы.
- Единые timeout/retry политики по контрактам из `docs/architecture/INTEGRATION_CONTRACTS.md`.
- Идемпотентность всех mutation-путей и async worker-операций.
- Наблюдаемость по состоянию сценария:
  - latency по шагам,
  - retry count,
  - compensation count,
  - terminal state (`Completed/Failed`).

## 6. Точки детализации в следующей итерации

- Разбивка сценариев на каталоги use-case (`HR`, `Compliance`, `Procurement` и т.п.).
- Формальная state machine для ключевых сценариев.
- Каталог компенсационных правил по каждому типу шага.
- Политика версионирования сценариев (backward compatibility).
